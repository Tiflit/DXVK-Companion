# Latest release metadata integrity

The fresh `releases/latest` response uses the same strict parser as the official catalog/tag lookup. It must identify a stable, non-draft canonical version and exactly one Windows archive named `dxvk-<version>.tar.gz` at its exact `github.com/doitsujin/dxvk/releases/download/<tag>/...` URL. Native/source archives are ignored, not used as fallback. Duplicate matching assets, malformed IDs/size/digest, unstable versions and mismatched URLs refuse the fresh response. The existing `ReleaseInfo` fields retain release/asset identity, declared size and optional SHA-256 digest in the cache.

Successful bodies are streamed through the existing 2 MiB metadata reader under the existing linked 15-second request timeout. ETag/304 behavior, cache lifetime, persisted failed-attempt throttling and concurrent check coalescing remain. Invalid responses follow the same failure path as an offline check: retain prior usable cached metadata, record the attempt and avoid repeated checks within the normal daily window. Checking metadata does not download an archive or update a game.

This is the first bounded latest-release integrity step under [#159](https://github.com/Tiflit/DXVK-Companion/issues/159), implemented by [#203](https://github.com/Tiflit/DXVK-Companion/issues/203). It validates newly fetched successful metadata only. Legacy cache compatibility and offline fallback are retained; old cache records are not retroactively origin-validated or upgraded into verified provenance. An optional digest in metadata is not evidence that downloaded bytes were checked or that an upstream signature exists.

Cache validator recovery in [#208](https://github.com/Tiflit/DXVK-Companion/issues/208) sends `If-None-Match` only for usable cached metadata with a parsed single non-wildcard ETag. Malformed, combined or wildcard cached values cause an ordinary unconditional request at the next due check, rather than a pre-request exception followed by a day of throttling. Newly returned ETags retain their complete representation, including `W/` for weak validators, across restart and subsequent conditional checks. A 304 refresh is accepted only after a usable conditional request; otherwise the existing failure path preserves prior metadata, records the attempt and throttles normally. These validators are HTTP cache hints, not package authenticity evidence. No cache schema or version-selection behavior changes.

The initial #203 metadata step did not change install-time extraction. [#205](https://github.com/Tiflit/DXVK-Companion/issues/205), with approved replacement scope #207, subsequently routes missing install-time payloads through the same existing official-release acquirer as explicit older-release downloads. [#210](https://github.com/Tiflit/DXVK-Companion/issues/210) covers explicit offline recovery below. Targeted packaged/device validation remains under the parent task. Restoration, pinning and Manual/Automated consent rules are unchanged.

Verification uses synthetic metadata/archive fixtures and fake HTTP handlers in existing cloud CI. Existing request-count, resource-disposal, persisted daily-check, first-run/local reuse and exact-version tests remain. Positive fixtures now model official metadata instead of accepting arbitrary archive names/hosts. New regressions exercise native/source distractors, rejected malformed/ambiguous identities with retained cache and throttling, optional digest persistence, legacy cache compatibility and streamed response limits. No actual package download, local app/test or device result is claimed by those fixtures.

## Install-time acquisition

For a missing eligible source version, the installer passes only its exact tag to its retained acquirer. The acquirer independently looks up official tag metadata; asserted cache/caller URLs, IDs and digests do not authorize acquisition. This adds an exact-tag metadata request when a payload is first needed, without adding a scheduled Latest check or a new endpoint. It reuses the acquirer's existing 128 MiB archive, 512 MiB decompression, 128 MiB DLL, entry and timeout bounds, checksum check when supplied, hidden staging, marker/manifest and non-overwriting publication. The old 60-second direct downloader is removed; the existing acquirer's 15-second metadata and 3-minute acquisition bounds apply instead. No new timeout parameter or format is introduced.

Required architecture/API completeness replaces the old nonempty-folder shortcut. Complete eligible local legacy/manual releases still work offline and retain their honest provenance limitations. Incomplete/invalid existing versions are preserved and refused, never automatically deleted or repaired. Newly acquired source is rechecked, and existing activity/library/profile checks still run after awaited acquisition before game mutation. A failed acquisition leaves game files untouched; a completed source may remain available if a subsequent game safety check refuses.

Within one installer, UI and install acquisition share the retained acquirer/gate. Same-store concurrent game mutations may still legitimately refuse under the existing 500 ms operation budget; coalesced package HTTP is not a promise that conflicting game operations both succeed. Separate application/acquirer instances may duplicate HTTP, while publication remains non-overwriting. The fallback exact-tag metadata client constructs an unused cache holder but never reads/writes the Latest cache; the old global EnsureDirectories call is gone. Public installer constructor signatures remain compatible.

Installer-level cloud fixtures cover valid publication/reconstructed offline reuse, hostile asserted URLs, truncated/digest-mismatched downloads with preserved game/older-release bytes, retry, partial existing-source refusal and Unknown activity after acquisition. First-run fixture archives use actual `dxvk-<numeric-version>` roots, support the extra exact-tag lookup and retain their original archive-request/lifecycle assertions. Their factory uses existing private real leases and an explicitly inactive synthetic process universe; dedicated Unknown-activity checks remain. No signature, authenticity of legacy/manual payloads, cross-process download coalescing or real-game validation is implied.

## Explicit offline recovery

Latest remains a policy, distinct from the concrete recorded managed version. An expired metadata cache can still identify an eligible local release after an offline check fails. With missing/corrupt/unusable metadata, Companion cannot establish Latest and reports that prerequisite instead of silently choosing another version. A known newer release whose payload cannot be acquired likewise refuses without replacing the installed release. Existing game files and restoration backups remain intact on these failures.

To use a complete downloaded release independently of Latest metadata, open Game Details, choose its exact **DXVK Version**, select **Save Settings**, then retry Enable/Update. This is an explicit pin using the existing selector; it does not claim the selected release is newest. The source must still meet the game's API/architecture requirements and existing payload integrity checks. Version selection remains locked while work is queued. Alternatively retain the installed version; if no local choice is usable, a network connection and the next daily metadata check/acquisition are required. Daily failure throttling is unchanged; reconnecting does not bypass it.

Update All now returns Failed for enabled Latest-target games whose metadata cannot be resolved, rather than omitting them and potentially presenting “already up to date.” Independent pinned updates still proceed. The batch retains a failure reason even when a later game succeeds, and clears stale reasons on a subsequent successful/no-op batch. This reports uncertainty, not an available-update claim.

Cache reads no longer create their parent directory. Save/failed-attempt persistence, corrupt-byte preservation and attempt sidecars retain their existing behavior. Hardware-free cloud regressions exercise verified acquired payloads with missing/corrupt metadata, explicit selection and service reconstruction without extra HTTP, known-newer failure followed by an explicitly selected older release, retained game/backup bytes, expired metadata reuse and batch result reporting. These are not GUI, real-upstream-package or real-device acceptance results; legacy/manual source provenance and cross-instance HTTP limits remain.
