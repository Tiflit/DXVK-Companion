# Latest release metadata integrity

The fresh `releases/latest` response uses the same strict parser as the official catalog/tag lookup. It must identify a stable, non-draft canonical version and exactly one Windows archive named `dxvk-<version>.tar.gz` at its exact `github.com/doitsujin/dxvk/releases/download/<tag>/...` URL. Native/source archives are ignored, not used as fallback. Duplicate matching assets, malformed IDs/size/digest, unstable versions and mismatched URLs refuse the fresh response. The existing `ReleaseInfo` fields retain release/asset identity, declared size and optional SHA-256 digest in the cache.

Successful bodies are streamed through the existing 2 MiB metadata reader under the existing linked 15-second request timeout. ETag/304 behavior, cache lifetime, persisted failed-attempt throttling and concurrent check coalescing remain. Invalid responses follow the same failure path as an offline check: retain prior usable cached metadata, record the attempt and avoid repeated checks within the normal daily window. Checking metadata does not download an archive or update a game.

This is the first bounded latest-release integrity step under [#159](https://github.com/Tiflit/DXVK-Companion/issues/159), implemented by [#203](https://github.com/Tiflit/DXVK-Companion/issues/203). It validates newly fetched successful metadata only. Legacy cache compatibility and offline fallback are retained; old cache records are not retroactively origin-validated or upgraded into verified provenance. An optional digest in metadata is not evidence that downloaded bytes were checked or that an upstream signature exists.

Cache validator recovery in [#208](https://github.com/Tiflit/DXVK-Companion/issues/208) sends `If-None-Match` only for usable cached metadata with a parsed single non-wildcard ETag. Malformed, combined or wildcard cached values cause an ordinary unconditional request at the next due check, rather than a pre-request exception followed by a day of throttling. Newly returned ETags retain their complete representation, including `W/` for weak validators, across restart and subsequent conditional checks. A 304 refresh is accepted only after a usable conditional request; otherwise the existing failure path preserves prior metadata, records the attempt and throttles normally. These validators are HTTP cache hints, not package authenticity evidence. No cache schema or version-selection behavior changes.

The initial #203 metadata step did not change install-time extraction. [#205](https://github.com/Tiflit/DXVK-Companion/issues/205), with approved replacement scope #207, subsequently routes missing install-time payloads through the same existing official-release acquirer as explicit older-release downloads. [#210](https://github.com/Tiflit/DXVK-Companion/issues/210) covers explicit offline recovery below. Targeted packaged/device validation remains under the parent task. Restoration, pinning and Manual/Automated consent rules are unchanged.

Verification uses synthetic metadata/archive fixtures and fake HTTP handlers in existing cloud CI. Existing request-count, resource-disposal, persisted daily-check, first-run/local reuse and exact-version tests remain. Positive fixtures now model official metadata instead of accepting arbitrary archive names/hosts. New regressions exercise native/source distractors, rejected malformed/ambiguous identities with retained cache and throttling, optional digest persistence, legacy cache compatibility and streamed response limits. No actual package download, local app/test or device result is claimed by those fixtures.

## Daily checks when persistence fails

Within one metadata client, each due Latest attempt also records its start time in private memory under the existing request gate. If both a cache save and failed-attempt recording fail, repeated and queued callers still share the normal 24-hour window. They receive prior usable on-disk metadata or null, preserving the existing fallback instead of exposing an unsaved fresh response. The next attempt is allowed at the exact 24-hour boundary; failed writes do not move that boundary on every call. Disk is re-read so repaired metadata can be used during the window.

This private fallback cannot survive client reconstruction when storage remains unwritable. Registered overlapping clients can also share it through the cache gate below. A successful cache or attempt write clears the private fallback, leaving persisted state authoritative. Cache schema, ETag rules, successful-validation timestamps, request bounds and explicit version selection remain unchanged. Fake HTTP/clock regressions cover failed staging/replacement, successful/304/error/cancelled responses, concurrent callers, unchanged cache bytes, exact boundary retry, external repair and reconstruction after a successful save. These are cloud fixtures, not local or device validation.

## Clients sharing a Latest cache

Separate clients in one process now share a gate keyed by normalized full cache-file path, using Windows case semantics. They re-read disk after waiting: a committed successful/304 response or failed-attempt timestamp satisfies queued callers without another request. Different cache files remain independent. The existing instance gate still protects each client's private attempt timestamp; lock order is instance gate then shared cache gate. No shared registry lock covers awaits or I/O.

If both result and attempt persistence fail, already registered participants pass the failed attempt timestamp under the shared gate and keep their own private daily window. They return current valid disk metadata or null, never an unsaved fresh result. The most recent shared/private timestamp wins. Gate registrations include queued/cancelled callers; idle entries are removed/disposed, retaining no global cache identity or unsaved timestamp. Thus a fresh client constructed after the entry retires cannot inherit an unwritable cache's unsaved window. Persistence is still needed for reconstruction and separate-process coordination. An unusable cache path that cannot be normalized retains the existing private-gate/network/cache-failure fallback; coordination does not turn it into a new pre-request exception.

Waiting cancellation releases its registration without cancelling the leader or writing an attempt. Cancelling the leader after HTTP starts retains the existing failed-attempt persistence/fallback behavior, which queued callers observe normally. Parser/ETag rules, 24-hour boundary, request timeout, schema, origin/trust and game/version behavior are unchanged. Fake HTTP/clock barriers cover success/304/failure, absent/valid unwritable caches, exact boundary/reconstruction, aliases, independent caches, cancellation and exception recovery. Same-user process coordination is described below; no all-physical-alias or device claim follows.

## Cooperating same-user processes

Before a due Latest HTTP attempt, Companion acquires the existing store-file lease keyed by canonical cache path in the existing same-user coordination namespace, using the approved 500 ms acquisition budget. It re-reads disk after acquisition and holds the lease through cache/attempt persistence. Busy or unavailable coordination returns current valid cached metadata or null, without HTTP, cache writes or an invented check timestamp; a later invocation can retry. Cancellation before HTTP likewise records no failed HTTP attempt. Fresh cache reads need no lease. Unnormalizable unusable cache paths retain the earlier private failure fallback; supported local paths use cross-process coordination.

Missing-release acquisition uses the same existing lease mechanism keyed by canonical exact destination path. It rechecks the destination after acquiring the lease and holds it through tag metadata, archive/integrity checks, staging, publication and owned cleanup. A busy/unavailable lease gives a fixed retry refusal with retained source bytes and no HTTP. Complete eligible local releases remain reusable offline before this lease is needed. Process-local gates remain first in the lock order; acquisition/tag lookup does not acquire a Latest cache lease or call back into game operations. Existing game ownership/activity/rollback safeguards remain separate.

No new lock format, service, endpoint, namespace, timeout setting or privilege is introduced. The existing DeleteOnClose handles release with disposal/process exit. Tests inject private coordination directories; production uses the existing same-user local-application-data locks directory. The 500 ms value is the existing acquisition budget; blocking filesystem operations can overshoot a wall-clock bound, so it is not a hard real-time guarantee. Existing 15-second metadata and three-minute archive limits remain. These are cooperative leases: older/noncooperating writers, direct CacheStore writes outside these HTTP paths, other users/machines, unsupported filesystems and all physical-path aliases are not newly synchronized. Persistence is still required to preserve a failed HTTP attempt across reconstruction; a lease cannot manufacture a record on unwritable storage.

Real-file/fake-HTTP regressions cover busy/unavailable leases, unchanged cache/source bytes, no fabricated attempts, cancellation, subsequent retry and complete-local reuse. Deterministic coordinator rendezvous cases also simulate a peer cache commit or verified acquired-release publication under a real OS lease while the caller waits; recheck must reuse it with zero caller HTTP. Two Windows GitHub Actions-only cases use the existing child protocol, 20-second total lifetime and four-second cleanup reservation to hold actual cache/destination lock files in another process: no HTTP while held, then normal progress after natural exit. Those cases validate cross-process exclusion around the real metadata/acquisition services; they do not launch a second full GUI, contact upstream or constitute packaged/device acceptance.

## Install-time acquisition

For a missing eligible source version, the installer passes only its exact tag to its retained acquirer. The acquirer independently looks up official tag metadata; asserted cache/caller URLs, IDs and digests do not authorize acquisition. This adds an exact-tag metadata request when a payload is first needed, without adding a scheduled Latest check or a new endpoint. It reuses the acquirer's existing 128 MiB archive, 512 MiB decompression, 128 MiB DLL, entry and timeout bounds, checksum check when supplied, hidden staging, marker/manifest and non-overwriting publication. The old 60-second direct downloader is removed; the existing acquirer's 15-second metadata and 3-minute acquisition bounds apply instead. No new timeout parameter or format is introduced.

Required architecture/API completeness replaces the old nonempty-folder shortcut. Complete eligible local legacy/manual releases still work offline and retain their honest provenance limitations. Incomplete/invalid existing versions are preserved and refused, never automatically deleted or repaired. Newly acquired source is rechecked, and existing activity/library/profile checks still run after awaited acquisition before game mutation. A failed acquisition leaves game files untouched; a completed source may remain available if a subsequent game safety check refuses.

Within one process, separate acquirer/client objects now share an acquisition gate keyed by normalized full destination path (library plus exact tag), using Windows path case semantics. The first caller acquires/publishes; waiting callers recheck local eligibility and reuse the complete release without another tag/archive request. Unrelated destinations remain independent. Gate registrations count holders and waiters, including cancelled/failed calls; idle entries are removed and their semaphores disposed after the last user leaves. A cancelled waiter does not cancel the leader; a live waiter may retry after a failed/cancelled leader. Existing request timeouts and cancellation ownership remain.

Within one installer, UI and install acquisition also share the retained acquirer. Same-store concurrent game mutations may still legitimately refuse under the existing 500 ms operation budget; coalesced package HTTP is not a promise that conflicting game operations both succeed. Cooperating same-user processes now use the bounded leases described above; contention returns cached fallback or an acquisition retry refusal. Latest clients in one process also share the cache gate. Normalized paths do not establish physical-file identity for every filesystem alias. Publication remains non-overwriting, including external collisions. The fallback exact-tag metadata client constructs an unused cache holder but never reads/writes the Latest cache; lazy coordination setup is unused for exact-tag lookup. Public installer/acquirer constructor signatures remain compatible.

Fake-HTTP barrier fixtures exercise separate clients/acquirers targeting one library/version, Windows case/trailing/dot path aliases, unrelated destinations, cancelled waiters/leaders, failed publication and pre-wait exceptions. Assertions verify request counts, complete manifest/payload reuse, preserved older sources and subsequent retry. These are process-local cloud fixtures, not cross-process or real-device acceptance.

Installer-level cloud fixtures cover valid publication/reconstructed offline reuse, hostile asserted URLs, truncated/digest-mismatched downloads with preserved game/older-release bytes, retry, partial existing-source refusal and Unknown activity after acquisition. First-run fixture archives use actual `dxvk-<numeric-version>` roots, support the extra exact-tag lookup and retain their original archive-request/lifecycle assertions. Their factory uses existing private real leases and an explicitly inactive synthetic process universe; dedicated Unknown-activity checks remain. No signature, authenticity of legacy/manual payloads or real-game validation is implied; cross-process contention has the explicit fallback/refusal behavior above.

## Explicit offline recovery

Latest remains a policy, distinct from the concrete recorded managed version. An expired metadata cache can still identify an eligible local release after an offline check fails. With missing/corrupt/unusable metadata, Companion cannot establish Latest and reports that prerequisite instead of silently choosing another version. A known newer release whose payload cannot be acquired likewise refuses without replacing the installed release. Existing game files and restoration backups remain intact on these failures.

To use a complete downloaded release independently of Latest metadata, open Game Details, choose its exact **DXVK Version**, select **Save Settings**, then retry Enable/Update. This is an explicit pin using the existing selector; it does not claim the selected release is newest. The source must still meet the game's API/architecture requirements and existing payload integrity checks. Version selection remains locked while work is queued. Alternatively retain the installed version; if no local choice is usable, a network connection and the next daily metadata check/acquisition are required. Daily failure throttling is unchanged; reconnecting does not bypass it.

Update All now returns Failed for enabled Latest-target games whose metadata cannot be resolved, rather than omitting them and potentially presenting “already up to date.” Independent pinned updates still proceed. The batch retains a failure reason even when a later game succeeds, and clears stale reasons on a subsequent successful/no-op batch. This reports uncertainty, not an available-update claim.

Cache reads no longer create their parent directory. Save/failed-attempt persistence, corrupt-byte preservation and attempt sidecars retain their existing behavior. Hardware-free cloud regressions exercise verified acquired payloads with missing/corrupt metadata, explicit selection and service reconstruction without extra HTTP, known-newer failure followed by an explicitly selected older release, retained game/backup bytes, expired metadata reuse and batch result reporting. These are not GUI, real-upstream-package or real-device acceptance results; legacy/manual source provenance and cross-instance HTTP limits remain.
