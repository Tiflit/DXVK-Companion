# Latest release metadata integrity

The fresh `releases/latest` response uses the same strict parser as the official catalog/tag lookup. It must identify a stable, non-draft canonical version and exactly one Windows archive named `dxvk-<version>.tar.gz` at its exact `github.com/doitsujin/dxvk/releases/download/<tag>/...` URL. Native/source archives are ignored, not used as fallback. Duplicate matching assets, malformed IDs/size/digest, unstable versions and mismatched URLs refuse the fresh response. The existing `ReleaseInfo` fields retain release/asset identity, declared size and optional SHA-256 digest in the cache.

Successful bodies are streamed through the existing 2 MiB metadata reader under the existing linked 15-second request timeout. ETag/304 behavior, cache lifetime, persisted failed-attempt throttling and concurrent check coalescing remain. Invalid responses follow the same failure path as an offline check: retain prior usable cached metadata, record the attempt and avoid repeated checks within the normal daily window. Checking metadata does not download an archive or update a game.

This is the first bounded latest-release integrity step under [#159](https://github.com/Tiflit/DXVK-Companion/issues/159), implemented by [#203](https://github.com/Tiflit/DXVK-Companion/issues/203). It validates newly fetched successful metadata only. Legacy cache compatibility and offline fallback are retained; old cache records are not retroactively origin-validated or upgraded into verified provenance. An optional digest in metadata is not evidence that downloaded bytes were checked or that an upstream signature exists.

The older install-time downloader/extractor remains a separate follow-up: this change does not give that path staged publication, bounded extraction, shared acquisition, manifest verification or authenticated local payloads. The explicit older-release acquirer has separate existing safeguards; do not infer them for every latest-release deployment. Local fallback selection, missing/corrupt-cache handling and targeted packaged/device validation remain bounded work under the parent task. Restoration, pinning and Manual/Automated consent rules are unchanged.

Verification uses synthetic metadata/archive fixtures and fake HTTP handlers in existing cloud CI. Existing request-count, resource-disposal, persisted daily-check, first-run/local reuse and exact-version tests remain. Positive fixtures now model official metadata instead of accepting arbitrary archive names/hosts. New regressions exercise native/source distractors, rejected malformed/ambiguous identities with retained cache and throttling, optional digest persistence, legacy cache compatibility and streamed response limits. No actual package download, local app/test or device result is claimed by those fixtures.
