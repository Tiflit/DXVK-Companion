## Limits and provenance

- Catalog: 30 entries per page, at most 32 constructed official pages; 2 MiB metadata per response; 15-second request timeout. Link headers are ignored. Explicit tag lookup verifies exact returned identity. Only stable, published `dxvk-<tag without v>.tar.gz` assets qualify; native/source packages do not.
- Acquisition: 128 MiB compressed, 512 MiB decompressed tar, 128 MiB per file, 256 entries, 3-minute download/extraction deadline plus caller cancellation. Buffered decompression is bounded; peak memory can exceed decompressed size because buffers and selected file bytes coexist. These limits accommodate observed official Windows packages (approximately 18 MiB compressed for current v3.1.1) without allowing unbounded archives. No external dependencies added.
- Only canonical x32/x64 known Windows DLL paths are written. Every supplied architecture must have a complete D3D11/DXGI pair or a D3D9-only payload; D3D9 is optional for older D3D11 releases. Existing API/architecture eligibility still controls deployment. Root scripts/license/readme are discarded, never executed. CRC32 and uncompressed length explicitly verify gzip trailers, including truncation.
- Supplied SHA-256 must match. Missing digest means official-origin metadata and local file hashes, not upstream checksum authentication. The manifest/marker is a consistency record, not a signature or protection against an attacker rewriting the entire library. A remaining marker prevents missing-manifest legacy downgrade; deleting both records makes historical acquisition indistinguishable from a manually populated library.
- Same-service calls coalesce by exact tag. Across processes, non-overwriting rename protects existing complete releases; duplicate downloads across processes are not prevented. Failed attempts only clean their own hidden staging directory. Invalid preexisting destinations are retained and refused rather than automatically deleted/repaired.
- The preexisting latest metadata cache and latest installer download/extraction path remain unchanged, including their older integrity limitations (#159). The new explicit acquisition path does not claim to repair all legacy sources. No schema, scheduling, anti-cheat, ownership, process-safety or restore-policy changes.

Sources inspected: official [DXVK releases](https://github.com/doitsujin/dxvk/releases) via GitHub API (current v3.1.1 includes distinct Windows/native assets), and GitHub's [release asset documentation](https://docs.github.com/en/rest/releases/assets) for browser URLs, redirects and optional digest. No third-party code or new licensed dependency incorporated; synthetic DLL bytes are test-owned text, never executed.

No observed human interruptions or new product decisions during implementation; no time/token savings inferred. Completion evidence will be a revision-bound PR comment rather than a journal-only CI refresh.
