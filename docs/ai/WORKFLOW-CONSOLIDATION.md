## Source-only fresh-session walkthrough

Inspected, not a launched agent or behavioral test:

1. An unfamiliar reviewer enters AGENTS, reads the kernel/unknown rules and compares all four identity paths against a trusted checkpoint. If the proposal is merged, its changed policy identity requires refreshed guidance. Inspecting a task label cannot authorize execution.
2. The reviewer obtains dashboard orientation and independently checks actual main/head/base and the task Issue's approval/hold/latest evidence. If the dashboard is unavailable, §6 routes to underlying records; unavailable remote facts remain unavailable.
3. For a release task, the map points to release client/acquirer/library, exact scoped tests and spec §§11–12/26/30/43, plus cross-cutting safety. The decision index points to #159/#165/#195 and their outstanding latest-downloader and provenance limits; it cannot mark those follow-ups complete.
4. For a failed helper test, the index points to the existing unknown-cause evidence and scoped CI diagnostics follow-up. A successful retry does not establish a runner fault; an optional improvement is not authority to edit out-of-scope tests or widen production waits.
5. The reviewer resumes from one task checkpoint's exact revisions, approvals/holds, findings, dirty-work preservation and next action, then follows original evidence links. No raw conversation transfer, new state database, agent lease, mandatory WIP push or automatic invocation is required or promised.

Relative file/section links and source/spec consistency are inspected before submission; existing cloud checks supply regression evidence. No new editorial tests, bootstrap runs, local suites or scanners are assigned. Self-review and a source walkthrough do not establish independent review or model obedience.

## Prospective documentation disposition (#188)

After human merge, the existing hygiene CLI and offline preflight require the existing `## Documentation` section to contain either:

- One entry per line, such as `- ` followed by a backtick-quoted `docs/guide.md`, an em dash and a short specific impact statement. Plain literal paths and hyphen separators also work. Multiple entries are allowed.
- `None — This repairs synthetic fixtures without changing public behavior.` Replace the example with the actual reason for this change.

Paths use portable literal repository-relative components and a documentation suffix (`.md`, `.rst`, `.txt`, `.adoc`). Absolute paths, URLs, traversal, empty components, backslashes and glob/encoded spellings fail. Explanations need at least four alphabetic words and 20 characters; obvious placeholders and generic no-change boilerplate fail. These conservative syntax heuristics cannot establish relevance, truth, completeness, privacy or freshness. Comments and fenced examples are not dispositions; duplicate Documentation headings fail. No additional heading or check context is introduced.

The one-argument `verify_pr_body(body)` API retains its historical heading-only behavior for existing consumers, including the guarded body updater. Its result explicitly labels disposition unverified. Callers opt into the new rule with `require_documentation=True`; CLI and preflight do so. Thus the updater alone is not a disposition gate. Its existing privacy/history/hash/backup safeguards remain unchanged. No historical description is rewritten and no historical failure is inferred.

`changed_files` and `repository_files` are optional complete lists of paths supplied explicitly to the validator; repository evidence must represent the proposed head. `None` means unavailable; an empty list asserts complete empty evidence and fails a cited path. Each supplied dimension is checked independently. Membership matches supplied evidence, not independently verified remote state. Deleted documentation may be included in changed evidence but is absent from head evidence; explain removals in remaining documentation or give a specific no-update reason. No filesystem lookup, Git process or network acquisition is performed by these checks.

Offline `run_preflight` exposes these inputs as `documentation_changed_files` and `documentation_repository_files`. Its existing scope manifest is not assumed complete for documentation and is never repurposed implicitly. The CLI has no new evidence flags and reports inclusion/existence unverified for path dispositions. Scope evaluation, rename handling and all Issue allowlists remain unchanged: a journal path or feature/fix branch grants no permission. There is no mandatory current-state edit or documentation churn requirement.

Actual enforcement uses whichever validator revision the existing workflow checks out. A historical base or external copy can still use older behavior; unadopted Agent-Workflow is not updated automatically. No new workflow, permission, automatic comment/PATCH, dependency, installation or bootstrap is added. Human review still assesses the actual disposition and any missing durable project memory.

## Provenance attribution after retries (#199)

Review packets and compact handoffs use the same execution-window selector for both `phase-a-test-results` and `build-provenance`. Artifact IDs/list order are not attempt chronology. Exactly one candidate must have a parseable creation timestamp within the triggering attempt's earliest job start and latest completion. Missing/invalid job intervals, missing candidate timestamps, no in-window match or multiple matches leave attribution unavailable; even a singleton is checked. Each supplied job must have a complete, non-reversed interval; this strengthens the existing TRX boundary rather than broadening it.

Selection precedes the existing JSON run/attempt/checkout/ref/base checks and handoff commit-parent verification. A timestamp match cannot excuse a stale JSON identity. Timestamp containment is server-metadata correlation, not a signature or content attestation; the existing collectors' API completeness and single-run acquisition limits remain. No new endpoint, authentication, permission, extraction/download budget, artifact producer or publication surface is added. Fixed selection/download diagnostics do not reproduce untrusted artifact metadata or exception contents. This repair improves availability of valid retry evidence; it does not resolve intermittent application failures or establish the privacy of original cloud artifacts.

## Synthetic lifecycle isolation and bounded diagnostics (#201)

`PersistedDeploymentLifecycleAcceptanceTests` and `PhaseDExternalChangesAndPendingActionTests` use the existing test-only `SyntheticSafetyFixture` factory. Their real stores, file leases and transaction engine remain; coordination files live under the fixture's owned storage root and its synthetic process universe is explicitly inactive. Reloaded services use the same owned namespace. Production constructors/defaults, 500 ms refusal and Unknown-activity behavior are unchanged. Activity/exclusion boundary tests keep their own explicit inspectors/coordinators rather than inheriting inactive activity assumptions.

A focused regression holds an unreadable unrelated target record constant, proves the actual inspector refuses in that namespace without publishing changes, and then proves the inspector detects the same replaced DLL through an independent fixture namespace. Existing same-namespace contention and explicit Unknown-activity refusal tests remain. This demonstrates the fixture mechanism; it does not reproduce or diagnose every historical CI failure.

The private store-lease setup and previously failing cloud child-helper test add fixed enum phase, elapsed milliseconds and coarse refusal-category messages. New messages omit raw exception text, paths, helper output/arguments and process/environment details. Non-null, task-reference, exact `LOCKED` signal, exit/cleanup and timing conditions remain equivalent; helper command and lifetime budgets are unchanged (2-second independent sleep, 12-second total, 4-second cleanup reservation). A self-exit deadline still fails via a fixed-message timeout exception and runs the existing cleanup. Do not infer scheduler/runner cause or general stability from a successful suite. Persistent failures remain tracked in #167 and need separately bounded diagnosis rather than timeout increases, retries until green or skipped tests.
