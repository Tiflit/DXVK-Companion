## Functional sequence

1. Execute the separately approved manual-management candidate after its review: upgrade/configuration/reapply/native-and-config restoration. Fix concrete failures with scoped production changes plus meaningful regressions before repeating any run under new authority.
2. Exercise remaining manual paths: DX9, existing official adoption, external-change/new-baseline and mixed-result batch restore. Group coherent cases rather than add a cosmetic PR for each control.
3. Validate detection/running-process deferral/restart/exit dispatch and supported API/architecture/anti-cheat refusals with an explicitly bounded process/game profile. Preserve conservative refusal when evidence is Unknown.
4. Validate an isolated real-game lifecycle and intended HUD/frame-limit effects; then expand Automated-mode scenarios. Broad compatibility/Experimental promotion and abrupt-termination recovery remain distinct decisions/evidence requirements.
5. Reconcile remaining specification clauses and failure boundaries before a stable standalone release. Optional startup, portable-folder moves, disabled/hidden tracking and packaging/documentation are functional release checks, not a reason to redesign the UI now.

This order may change for a concrete safety defect. It neither dispatches models nor authorizes host execution, cleanup, a crash simulation, new dependencies or a changed recovery guarantee. Existing ended profiles/evidence remain ended and retained. No implementation defect is asserted solely because packaged evidence is missing.
