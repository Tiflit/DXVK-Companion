# Persisted Update All and Restore All Mixed-Result Lifecycle Acceptance — #293

Service-level acceptance coverage for an integrated acquired-source -> persisted `UpdateAllEnabled` -> persisted `RestoreAll` mixed-result lifecycle, demonstrating that a failure in one game neither blocks other games nor disappears behind later successes, with error isolation, traversal order verification, and durable history preservation across service reloads.

## Scope and Model

Under Companion's architecture and specification sections 18, 20, and 23:
1. **Batch Operations with Error Isolation (Section 23)**: When executing batch operations across multiple managed games:
   - In `UpdateAllEnabledAsync`, each enabled profile is updated independently. If an update fails for one game (e.g. because a pinned version is unavailable), subsequent games continue to be evaluated and updated. A later success does not erase the failure from the returned dictionary, and the overall `LastRefusalReason` retains the batch refusal diagnostic for presentation. Already-restored or current installations are excluded from updates.
   - In `RestoreAllAsync`, every managed installation (`Managed` or `AttentionRequired` with active managed version) is restored independently under multi-file transaction safety. A transaction failure on one game (e.g. backup hash mismatch) does not abort restores on other games. The returned `RestoreAllSummary` accurately counts `TotalManaged`, `Restored`, `FailedOrAttentionRequired`, `AlreadyRestored`, and `QueuedRunning`.
2. **Attribution and Diagnostics Integrity**: Diagnostic messages generated by batch failures specifically identify the failed target by executable name and diagnostic reason, without falsely attributing the failure to unrelated healthy or already-restored targets.
3. **Truthful Durable History**:
   - Targets created through a real install/disable lifecycle remain in `RestorationState.Restored` with cleared active version, intact baseline backups, and historical ownership records.
   - Restored targets are counted as `AlreadyRestored` in subsequent restore operations.
   - A failed target retains active management and documented refusal diagnostics without false transitions to restored/disabled state, without pending actions, and without silent repairs.
4. **Traversal Order and Profile Enumeration**: Profiles are enumerated in deterministic order from `ProfileStore.GetAll()`. Traversal order is validated using a bounded two-case theory (`BeforeHealthyTargets` where the failing target precedes healthy targets, and `BetweenHealthyTargets` where the failing target is sequenced between healthy targets).
5. **Fresh Service Reconstruction & Offline Isolation**: All services, stores, and managers are reconstructed from disk at each lifecycle boundary. The HTTP transport is marked unavailable after initial release acquisition, ensuring zero additional network requests across all subsequent operations.

## Acceptance Scenarios

### `MixedBatchLifecycle_UpdateAllAndRestoreAll_MixedResultsPreserveErrorIsolationAndDurability`

Evaluated on DX11/x64 across two traversal orders:
- **`BeforeHealthyTargets`**: Profiles inserted and enumerated in order `[GameB, GameA, GameC, GameD]`.
- **`BetweenHealthyTargets`**: Profiles inserted and enumerated in order `[GameA, GameB, GameC, GameD]`.

#### 1. Pre-Deployment Setup & Acquisition
- Acquires official releases `v2.5` and `v2.6` into the shared library with verified markers, manifests, and architecture payloads.
- Fake HTTP transport is marked unavailable (`RejectAllRequests = true`) after initial acquisition.
- Four distinct targets created:
  - **Game A**: inert `GameA.exe`, native `d3d11.dll` (Existing baseline), absent `dxgi.dll` (Missing baseline), preexisting user `dxvk.conf` with lookalike keys (`dxvk.hudExtra`, `dxvk.maxFrameRateTarget`) and user lines, sentinel file, empty subdirectory.
  - **Game B**: inert `GameB.exe`, native `d3d11.dll` (Existing baseline), absent `dxgi.dll` (Missing baseline), preexisting user `dxvk.conf`, sentinel file, empty subdirectory.
  - **Game C**: inert `GameC.exe`, native `d3d11.dll` (Existing baseline), absent `dxgi.dll` (Missing baseline), absent `dxvk.conf` (synthetic Missing baseline for config), sentinel file, empty subdirectory.
  - **Game D**: inert `GameD.exe`, native `d3d11.dll` (Existing baseline), absent `dxgi.dll` (Missing baseline), preexisting user `dxvk.conf`, sentinel file, empty subdirectory.

#### 2. Initial Deployment & Truthful History
- Configures isolated `SettingsStore` Manual global policy (`GlobalManagementPolicy.Manual`).
- Deploys Game D through real enable (`RequestEnableByPathAsync`) and disable (`RequestDisableByPathAsync`) to establish truthful durable history (`RestorationState.Restored`, cleared managed version, retained historical ownership).
  - Before disable, performs deployed ownership, hash, and exact configuration checks via `ParseConfigAssignments` (asserting `dxvk.hud == "fps,devinfo"`, `dxvk.maxFrameRate == "60"`, user key `user.settingD == "4"`, and `ExpectedManagedSha256` matching deployed DLL and config bytes).
  - After disable, verifies `AssertRestoredHistory` for Game D.
- Deploys Game A, Game B, and Game C via single-call `RequestEnableByPathAsync` under `UseGlobal` manual policy with exact older selector `v2.5` without targetVersion override.
- Verifies unconditional `ExpectedManagedSha256` comparisons against deployed game bytes for DLLs and configs.
- Verifies exact configuration assignments via `ParseConfigAssignments`:
  - Game A: generated keys (`dxvk.hud`, `dxvk.maxFrameRate`), preserved lookalikes (`dxvk.hudExtra`, `dxvk.maxFrameRateTarget`), user line `user.settingA`.
  - Game B: generated keys, preserved lookalikes, user line `user.settingB`.
  - Game C: only generated keys (`Count == 2`), no lookalike or user keys.
- Verifies original native/config baselines and backup files across all targets.

#### 3. Selector Modification & `UpdateAllEnabledAsync`
- Reconstructs stack from disk. Verifies persisted policy and reloaded selector/API/architecture intent on all targets before modifying selectors (`profile.Api`, `profile.Architecture`, `profile.DxvkVersion`, `profile.DxvkEnabled`, `inst.ManagementPolicy.Mode`, `inst.ManagementPolicy.PinnedDxvkVersion`, `inst.ManagedDxvkArchitecture`, executable API and architecture).
- Updates only persisted selectors: Game A and Game C select `v2.6`; Game B selects deliberately unavailable `v2.7-unavailable`. Game D remains unselected. Does not preassign profile actual versions.
- Snapshots complete raw Game B resources, complete backups directory (`preUpdateBackupsSnapshot`), and captures meaningful ownership before update.
- Reconstructs stack from disk and calls `UpdateAllEnabledAsync()`.
- Verifies:
  - Traversal order matches profile enumeration order (`[GameB, GameA, GameC]` or `[GameA, GameB, GameC]`).
  - Game A: `Applied`, updated to `v2.6`, release DLLs deployed, `ExpectedManagedSha256` matching deployed bytes, original baselines intact, configuration assignments verified via `ParseConfigAssignments`.
  - Game B: `Failed`, actual version remains `v2.5`, selector remains `v2.7-unavailable`, complete raw game directory and backups completely unchanged (`AssertResourcesUnchanged(preUpdateBackupsSnapshot, backupsDir)`), ownership matches pre-update state.
  - Game C: `Applied`, updated to `v2.6`, release DLLs deployed, `ExpectedManagedSha256` matching deployed bytes, original baselines intact, configuration assignments verified via `ParseConfigAssignments`.
  - Game D: intentionally omitted from results dictionary.
  - Retained batch refusal reason: `manager.LastRefusalReason` retains Game B's unavailable version diagnostic despite subsequent healthy successes.
  - Zero additional HTTP calls.

#### 4. Backup Fault Injection & `RestoreAllAsync`
- Corrupts Game B's recorded original native backup (`Backups/<idB>/d3d11.dll`) while leaving its managed game DLL bytes in `GameB` intact.
- Snapshots faulted backup, game, and source state and captures meaningful ownership.
- Reconstructs stack from disk and calls `RestoreAllAsync()`.
- Verifies:
  - `TotalManaged`: 3 (Games A, B, C)
  - `Restored`: 2 (Games A, C)
  - `FailedOrAttentionRequired`: 1 (Game B)
  - `AlreadyRestored`: 1 (Game D)
  - `QueuedRunning`: 0
  - Diagnostic messages: single message identifying `GameB.exe:` with backup hash mismatch, with no false attribution to Games A, C, or D.
  - Games A and C match their complete original raw file/directory snapshots.
  - Game B resources (game, sources, faulted backup) remain completely untouched. Active management retained with exact faulted ownership verified via `AssertFaultedOwnershipRetained` (verifying `AttentionRequired`, refusal diagnostic containing "backup hash mismatch", null `PendingAction`, and exact versions, policy, configs, executables, and managed records retained).
  - Zero additional HTTP calls.

#### 5. Reload, Historical Ownership, and Repeat `RestoreAllAsync`
- Reconstructs stack from disk.
- Verifies exact nonempty historical ownership sets via `AssertRestoredHistory` for restored Games A, C, D with cleared active versions, truthful retained baselines, and preserved backup files.
- Verifies Game B remains in `AttentionRequired` with active management and exact faulted ownership retained via `AssertFaultedOwnershipRetained`.
- Repeats `RestoreAllAsync()`:
  - `TotalManaged`: 1 (Game B)
  - `Restored`: 0
  - `FailedOrAttentionRequired`: 1 (Game B)
  - `AlreadyRestored`: 3 (Games A, C, D)
  - `QueuedRunning`: 0
  - Message identifies `GameB.exe:` backup hash mismatch.
- Reconstructs fresh stack from disk. Verifies `AssertRestoredHistory` on Games A, C, D and `AssertFaultedOwnershipRetained` on Game B.
- Verifies Game B remains safely unresolved without silent repair and restored resources remain unchanged.
- Verifies complete retained backup file set (7 backup files across the 4 installations).
- Verifies sources remain intact.
- Zero additional HTTP calls throughout the entire suite.
