# Bounded cloud lock-helper protocol

[#212](https://github.com/Tiflit/DXVK-Companion/issues/212) repairs a timing assumption in the existing Windows/cloud-only lock helpers. Previously the child printed `LOCKED` and independently released after two seconds. A parent delayed beyond that window could legitimately acquire the now-free lock while its test still asserted exclusion. This source-level race does not establish the exact cause of every historical CI failure.

The child now holds its real exclusive DeleteOnClose handle while waiting for an operation-owned `self-exit.signal` inside the private synthetic coordination directory. The parent receives `LOCKED`, completes the existing 200 ms refusal attempt, then writes the marker. The child checks that two seconds remain, emits `TIMER_STARTED`, and performs its unchanged two-second independent self-exit. The parent requires successful natural exit and subsequent 500 ms lease acquisition. No marker is shared outside that fixture or retained as product state.

The pre-arm hold is synchronized rather than fixed at two seconds; total lifetime limits do not increase. The existing successful helper has 20 seconds total, the timeout helper 12 seconds, each retaining four seconds for cleanup. An absolute deadline is derived before process startup; the child subtracts startup time then uses a monotonic stopwatch for its remaining watchdog. Missing arming causes independent exit 2. Insufficient remaining time exits 3; overrun after the self-exit interval exits 4. Unexpected helper exceptions exit 1 without echoing raw details. Parent deadline failures remain failures, not skips or retries. Existing owned-process kill and cleanup bounds remain.

Private signal/exit I/O helpers avoid unnecessary context capture, while test methods retain xUnit's synchronization context and parallelization limits. Direct `ConfigureAwait(false)` in tests would violate [xUnit1030](https://xunit.net/xunit.analyzers/rules/xUnit1030); no analyzer suppression or project setting change is used. Fixed phase/category/elapsed diagnostics distinguish startup, exclusion, arming and self-exit without dumping lease objects or child output. These scheduling choices do not diagnose earlier failures by themselves. A passing run cannot prove universal runner stability.

Regression coverage includes a deliberate 2.2-second parent delay beyond the old hold window, a missing-arm watchdog case that must exit naturally without parent kill, unchanged real exclusion/post-exit acquisition checks, and diagnostic privacy checks. The delayed case uses the existing 20-second budget; the missing-arm case uses a two-second child watchdog inside the existing 12-second parent/cleanup budget. No global collection serialization, coordinator production change, timeout widening, workflow/dependency/project change or local execution profile is introduced. These helpers execute only under the existing Windows GitHub Actions guard; no local helper, app, game or device result is claimed.

## Dedicated child-process collection

[#214](https://github.com/Tiflit/DXVK-Companion/issues/214) moves the four `InterProcessLocking_*` methods (five data cases) and their private protocol helpers verbatim from `OperationLeaseCoordinatorTests` to `CloudLockHelperTests`. Historical evidence uses the former class prefix; method names and cases are unchanged. The new class uses the `Cloud lock helpers` collection with `DisableParallelization = true`, as supported by [xUnit collection isolation](https://xunit.net/docs/running-tests-in-parallel#opting-a-test-collection-out-of-parallelism). Those child-process cases run separately from other collections; remaining coordinator/application tests retain ordinary parallel execution and explicit in-test concurrency checks. No assembly-wide serialization setting changes.

The post-#213 main failure was startup at 8,004 ms before LOCKED, plus an independent lifecycle fixture's unexplained initial refusal. The old hold-window race and these failures are distinct. Collection isolation reduces interference at the functional helper boundary; it does not prove a specific resource/runner cause or guarantee all deadline failures disappear. The lifecycle fixture now reports only a fixed Apply/Reapply/Restore phase, elapsed time and whitelisted refusal category if its existing boolean assertions fail. It retains every baseline/file assertion. All helper bodies, child watchdog/script, guards and deadlines remain unchanged by the move. Existing helper regressions remain the verification cases; a second bounded same-head full run checks repeatability without treating retries as a repair.

The first isolated-layout run still failed: a delayed helper reached exclusion after its operational deadline, and a separate shared-directory restore fixture failed. Isolation alone is therefore not accepted as a complete fix. A focused diagnostic delta adds numeric parent process-start/signal/delay/probe milestones, task status, thread-pool counts and a fixed child Running/Exited/Unavailable state to failure messages. It does not print paths, process identifiers, arbitrary output or exception text, and changes no child script, test conditions or budgets. These metrics distinguish where time was consumed; they do not by themselves prove its cause.
